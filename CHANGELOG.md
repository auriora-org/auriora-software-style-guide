# Changelog

All notable changes to the AURIORA Software Style Guide are documented in this file. Released versions are tagged in version control.

## 0.4.0 - 2026-09-18

- Stored object retrieval and the Module Hub host-facing interface on the host side (§3.5), following AES 0.9.0 `AES-MCI-008` and `AES-HUB-003` ([EDR-010](https://github.com/auriora-org/auriora-engineering-standard/blob/main/docs/edr/EDR-010-hub-host-facing-interface-and-stored-object-retrieval.md)): a Hub is reached through its host-facing interface with the same binding as a Module and is an addressable device plus a transport hop, never a reason to special-case the Modules behind it; download by reading, not by session — enumerate, read metadata, read by identity/offset/length within the declared chunk maximum, verify every response's object/offset/length, keep the resume point on the host as the byte count stored and continue after any interruption by rediscovering the Module by identity; verified means matching the inventory hash, partial files stay marked partial, vanished or changed objects are reported and never retried against a different object; provenance (run, segment, deployment, Session, time and sample range, format, firmware) is read from the recording's metadata and never inferred from the connection, with one code path for coordinated, Hub-connected and standalone recordings and one object per segment; bulk runs behind control traffic one chunk at a time and a control operation is expected within one chunk; retrieval is read-only and deletion is a separately declared, explicitly requested operation refused during an armed or running run. §3.6's deployment record now includes the identity and verified integrity value of every retrieved recording and log.

## 0.3.0 - 2026-09-17

- Experiment compilation and deployment rules (new §3.6), following AES 0.8.0, which superseded the Module Synchronization Interface with the AURIORA Event Link (`AES-AEL-001` to `AES-AEL-005`, EDR-008): compile the experiment description into a deployment plan — Sessions and Assets, a semantic-event → event-identifier map, per-Module AEL receive and source bindings and per-Hub route tables — rather than scripting commands, with no researcher ever authoring routes or identifiers and no experiment language standardized; allocate identifiers per deployment, unique across the whole AEL routing domain, never `0x0000`, and store the map before arming; keep known timelines in Module Sessions and route over AEL only what cannot be scheduled; validate the plan against the discovered bench — identities, capabilities, Assets, route realizability, Hub route/queue/rate capacity, acyclic Hub-to-Hub topology, accumulated latency against published envelopes, resources and safety limits — and refuse with the reason named; find cycles in the event/action graph and refuse any that no Module-side guard bounds; deploy in order (transfer, stage, validate, commit and read back route identities, arm and confirm, and only then the experiment's initiating AEL event — a `T0` where the experiment has one, otherwise the detector, external or Module event that starts it); never replace an active route table while a dependent Module is armed or running; record everything needed to reconstruct the run, including counters, ignored/invalid/unrouted/overflowed events, and build counter reconciliation into the tool; reconnect by reading actual state and never re-arm, re-commit or restart; and simulate AEL routers and links, not only Modules. §3.5 updated: the deterministic event is an AEL event, and the experiment record includes the AEL topology, identifier map and committed route tables.
- Unattended deployment rules (§3.6), following AES 0.8.0 `AES-MCI-006`/`AES-MCI-007` ([EDR-009](https://github.com/auriora-org/auriora-engineering-standard/blob/main/docs/edr/EDR-009-autonomous-module-operation-and-recovery.md)): a single Module on a local cable with no Hub and no AEL is deployed by the same steps; a Module that will run without the host is planned only from its declared autonomous continuation and deployment policy behaviors — host loss, recovery after reset, storage exhaustion — refused by name where a needed behavior is missing, configured only from the declared set with the Module's refusal taken as the answer, storage-checked where capacity and rate are known, and its policy persisted exactly as read back together with its persistent-deployment-state identity before arming; the policy is modelled apart from the Session; autonomous behavior is shown in UI, CLI and record rather than buried in defaults; the deployment record gains the policy, persistent-state identity, run segments with their boundaries (reset cause, last/first local time and sample index, time-reference status, authorizing policy), storage-exhaustion events and overwritten extent, and segment reconciliation joins counter reconciliation in the tool; reconnection additionally reads recovery occurrence and count, run and segment identity, reset cause, completion/stop/refusal reason and storage state, never infers state from USB path, Hub port, process memory or UI, and treats a Module found `IDLE` with a recorded refusal as a question for the person.
- **Local by default** (§1): device control and experiment capture SHOULD run with no Internet access, no cloud service and no vendor account, unless network connectivity is intrinsic to the workflow itself; optional remote access, synchronization, collaboration and monitoring are unaffected.
- Security (§15): the written threat model requirement is scoped — "none" is a conclusion, not a default, a disposable script writes one line, and the paragraph is owed where software updates firmware, accepts network connections, drives devices in a maintained workflow or stores research data. Aligns the rule with the Firmware Style Guide, which already carried the same clause.

## 0.2.0 - 2026-09-12

- Module fleet rules (§3.5): key the device registry on the Module's persistent identity as reported over the Module Control Interface, never on a device node, port path or hub position, and hold physical location as a mutable attribute of the identified Module so that moving one updates its location while replacing one is recognized as a different device; take feature decisions from reported capabilities rather than a product-number table; query the Module's inventory and content integrity values and transfer only what differs; express experiment setups as desired state and diff against what each Module reports; keep logical groups host-side, where they work identically for locally connected and hub-connected Modules; confirm every required Module actually armed and refuse to proceed by name when one did not, and never use a control command as the simultaneous trigger for several Modules — the deterministic instant is a SYNC event; treat discovery as establishing identity and nothing more; record every participating Module's identity, firmware version and configuration plus the SYNC topology in the experiment record; and let the simulated device of §3.4 speak the same control semantics. The interface itself is defined by AES 0.7.0 (`AES-MCI-001` to `AES-MCI-005`).

## 0.1.0 - 2026-07-13

First release.

- Design philosophy and a maturity-scaling model: damage-prevention rules always; reproducible builds, packaging and platform-support claims bind Released software; the layered architecture is the model tools converge on as they mature. A small script is allowed to remain a small script.
- Software architecture: layered model (presentation, application, device communication, transport), module responsibilities, dependency injection, pure logic separation.
- Device communication: protocol specification as the contract, layering and isolation, robustness rules, simulated devices for development and testing.
- Project structure, language and toolchain policy, coding style, API design and error handling guidance.
- Concurrency, dependency management and configuration rules.
- Logging and diagnostics including wire-level protocol tracing (required for Released device tooling).
- Command-line and user interface conventions, data format and storage rules.
- Security, testing, packaging and distribution requirements scaled to maturity.
- Versioning and device compatibility rules aligned with the AURIORA Engineering Standard.
- Documentation requirements aligned with the AURIORA Documentation Standard.
- A compact code review checklist (every change / device communication / toward Release); self-review explicitly valid.
- Requirement language aligned with AES (MUST/SHOULD/MAY; a skipped SHOULD needs no documented exception).
- Language-independent policy: no language-, framework- or vendor-specific rules.
